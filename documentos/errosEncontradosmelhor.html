O que é um Code Smell?

Na engenharia de software, code smells são sintomas de que algo está errado no design ou na implementação, prejudicando manutenção, testabilidade e evolução do sistema. Os problemas abaixo foram classificados segundo a escala de severidade baseada em MVC e SOLID.

SeveridadeCritério
Critical Falhas graves de segurança ou arquitetura — expõem dados, permitem ataques ou violam completamente a separação de responsabilidades
High Violações fortes de MVC/SOLID — acoplamento excessivo, lógica no lugar errado, dificultam manutenção e testes
Medium Problemas de padronização, duplicação ou performance moderada — queries N+1, magic numbers, validações ausentes
Low Melhorias de legibilidade — nomenclatura ruim, variáveis obscuras, código desorganizado

01 SQL Injection — SELECT via concatenação (GET produtos)
linha 28 Critical ▼
SQL Injection Falha de Segurança models.py:28 
cursor.execute("SELECT * FROM produtos WHERE id = " + str(id))

Concatenação direta de input do usuário na query SQL. Qualquer valor passado como id é interpretado como parte do comando SQL — um atacante pode enviar 1 OR 1=1 ou 1; DROP TABLE produtos e obter ou destruir dados.

Por que é Critical SQL Injection é uma das vulnerabilidades mais exploradas do mundo (OWASP Top 1). Uma única requisição maliciosa pode expor toda a base de dados ou corrompê-la permanentemente. Não requer autenticação para ser explorada.
Solução Usar parâmetros parametrizáveis — nunca concatenar valores externos diretamente na query: 
cursor.execute("SELECT * FROM produtos WHERE id = ?", (id,))

07 Query N+1 em loop de itens do pedido
linha 139 High ▼
Query N+1 Bloatheads Performance models.py:139 
for item in itens:
    cursor.execute("SELECT * FROM produtos WHERE id = " + str(item["produto_id"]))
    produto = cursor.fetchone()

Para cada item do pedido é executada uma query separada ao banco. Se o pedido tiver 50 itens, são 50 queries individuais — o que poderia ser resolvido com uma única query usando IN (...).

Por que é High Em sistemas com volume moderado de pedidos, isso degrada a performance significativamente. Contém também SQL Injection secundário pelo str(item["produto_id"]).
Solução — buscar todos os IDs em uma única query 
ids = [item["produto_id"] for item in itens]
placeholders = ",".join("?" * len(ids))
cursor.execute(f"SELECT * FROM produtos WHERE id IN ({placeholders})", ids)
08 Cursores aninhados — pedidos por usuário (Callback Hell)
linha 173 High ▼
Callback Hell Cursores Aninhados Bloatheads models.py:173 
cursor = db.cursor()
cursor.execute("SELECT * FROM pedidos WHERE usuario_id = " + str(usuario_id))
rows = cursor.fetchall()
for row in rows:
    cursor2 = db.cursor()
    cursor2.execute("SELECT * FROM itens_pedido WHERE pedido_id = " + str(row["id"]))
    itens = cursor2.fetchall()
    for item in itens:
        cursor3 = db.cursor()  # terceiro nível

Três cursores aninhados (cursor, cursor2, cursor3) para buscar pedidos, itens e produtos em loops encadeados. Estrutura análoga ao Callback Hell — cada nível adiciona complexidade e dificulta rastreamento de erros.

Por que é High Além da ilegibilidade, gera N+1 em dois níveis. Qualquer mudança no schema impacta os três níveis de aninhamento simultaneamente.
Solução Substituir por JOINs ou queries únicas com mapeamento posterior em Python.

params = []

if categoria:
    conditions.append("categoria = ?")
    params.append(categoria)

linha 289 Medium ▼
Código Duplicado DRY Violation models.py:289

O padrão query += " AND campo = '" + valor + "'" é repetido 4 vezes com variações mínimas. Qualquer refatoração para usar parâmetros exigirá modificar todos os 4 pontos separadamente.

Por que é Medium — Código Duplicado Viola o princípio DRY. Se uma regra muda (ex: adicionar sanitização de termo), precisa ser aplicada em múltiplos lugares. A chance de inconsistência é alta — especialmente em código de segurança.
Solução Centralizar a construção da query em um helper reutilizável que receba os filtros como dicionário.
